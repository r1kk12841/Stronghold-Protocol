# Android App Implementation Plan

This document is an execution plan for Gemini or another coding agent. It describes how to add an Android client without rewriting the game or embedding the Node.js server in the APK.

## 1. Goal

Produce an installable Android APK/AAB for **Stronghold Protocol: Covenant** that:

- uses the existing browser game and Node.js/WebSocket server;
- supports English and Chinese exactly as the web client does;
- works with a LAN server during development and an HTTPS/WSS server in production;
- preserves touch controls, WebGL/PixiJS/Spine rendering, audio, reconnect tokens, and room invitation links;
- does not commit or package copyrighted game assets into Git;
- can later be prepared for Google Play without changing the gameplay engine.

## 2. Architectural decision

### MVP: Capacitor remote-client shell

Build a small Capacitor Android application whose bundled page lets the user select a game server, checks that server's `/healthz` endpoint, saves the URL, and then navigates the WebView to that server.

Once navigation is complete, the existing application remains same-origin with its server. Therefore all current absolute paths keep working unchanged:

- `/data/*.json`
- `/assets/**`
- `/shared/**`
- `/sim/**`
- `/ws`

The existing `defaultWsUrl()` in `public/js/net.js` will automatically select `ws://` or `wss://` from the loaded server URL. Do not add a second networking stack for the MVP.

The Android application is a **client only**. The Node.js server is still run on a PC, VPS, or other host. Do not attempt to run `server/index.js` inside Android.

### Why this is the first implementation

- It avoids refactoring every root-relative data, simulation, audio, image, and Spine URL.
- It avoids putting roughly 250 MB of downloaded game assets in the base APK.
- Web and Android clients use exactly the same deployed game version.
- Server updates immediately update the game client without shipping a new APK.
- Existing WebSocket reconnect behavior and browser-side simulation remain intact.

### Explicit MVP limitations

- The app needs access to a running Stronghold Protocol server.
- The WebView loads remote game content after the server-selection screen.
- LAN servers commonly use cleartext HTTP. This must be enabled deliberately and documented as a LAN-only compromise.
- A remote-content wrapper may require additional native value before public Google Play submission. Store publication is a later phase, not an MVP acceptance criterion.

Do not switch to a bundled/offline web client during MVP implementation. That is Phase 8 and requires a separate design review.

## 4. Phase 0 — prerequisites and baseline

Before editing:

1. Run `git status --short`. Preserve unrelated work.
2. Run the existing focused client tests:

   ```bash
   node --test test/client-static.test.js test/ui/gameLogic.test.js test/ui/i18n.test.js
   ```

3. Confirm the web server starts and `GET /healthz` returns HTTP 200.
4. Record the installed Node version.
5. Install Android Studio and an Android SDK supported by the selected stable Capacitor major.

Use one stable Capacitor major for `@capacitor/core`, `@capacitor/cli`, and `@capacitor/android`. All three package versions must match. Do not mix stable and `next` releases. Consult the official environment and Android documentation before selecting the major:

- <https://capacitorjs.com/docs/getting-started/environment-setup>
- <https://capacitorjs.com/docs/android>

Commit the resulting lockfile.

## 5. Phase 1 — initialize Capacitor

Install dependencies as development dependencies unless the chosen Capacitor documentation requires otherwise:

```bash
npm install --save-dev @capacitor/core @capacitor/cli @capacitor/android
```

Initialize with these values:

```text
appId: io.github.r1kk12841.strongholdprotocol
appName: Stronghold Protocol
webDir: android-shell/www
```

Create `capacitor.config.ts`. Required settings:

- `webDir` points to `android-shell/www`.
- Android uses the HTTPS-compatible scheme recommended by the selected stable Capacitor release.
- Navigation is allowed only after validation by the shell. If Capacitor requires a static `allowNavigation` list for runtime-selected LAN hosts, use the narrowest supported rule and document why it exists.
- Do not hard-code a personal server, API token, password, or signing value.

Then run:

```bash
npx cap add android
npx cap sync android
```

Add scripts to `package.json`:

```json
{
  "android:sync": "npx cap sync android",
  "android:open": "npx cap open android",
  "android:run": "npx cap run android",
  "android:debug": "npm run android:sync && cd android && gradlew assembleDebug",
  "android:bundle": "npm run android:sync && cd android && gradlew bundleRelease"
}
```

Use `gradlew.bat` on Windows if a cross-platform npm script cannot reliably select the wrapper. A small Node launcher script is preferable to shell-specific conditionals.

Acceptance criteria:

- `npx cap sync android` completes without warnings about a missing `webDir`.
- Android Studio opens the generated project.
- A blank shell installs and launches on an emulator or physical device.

## 6. Phase 2 — server-selection shell

Implement `android-shell/www/index.html`, `app.css`, and `app.js` with no framework dependency.

### Required UI

- Project title and fork/original-project credit.
- Server URL input.
- Examples:
  - Emulator: `http://10.0.2.2:3000`
  - Physical device on LAN: `http://192.168.1.20:3000`
  - Production: `https://game.example.com`
- **Connect** button.
- **Use last server** action when a saved URL exists.
- Loading state, validation error, health-check error, and offline message.
- Short warning that `http://` should only be used on a trusted LAN.
- Chinese/English copy or language-neutral labels. Do not reuse the game's translation runtime because the shell must work before the server loads.

### URL normalization rules

Create pure functions and tests for these rules:

1. Trim whitespace.
2. If no scheme is supplied, default to `http://` for an IP/localhost and `https://` for a hostname.
3. Accept only `http:` and `https:`.
4. Reject embedded credentials, fragments, unsupported ports, invalid hostnames, and non-root pathnames.
5. Remove trailing slashes.
6. Preserve an optional `?room=KEY` only when `KEY` matches the existing room-key format.
7. Never inject the URL through `innerHTML`.

### Connection flow

1. Normalize the URL.
2. Fetch `${origin}/healthz` with a short timeout.
3. Require `response.ok` and JSON with `ok === true`.
4. Save only the normalized origin in local storage.
5. Navigate the current WebView to the origin, optionally restoring `?room=KEY`.
6. Provide a retry path without clearing the saved URL.

Add a way to return to server selection:

- Preferred: a native overflow/menu action named **Change server** that clears only the shell's selected-server preference and loads the bundled shell page.
- Acceptable MVP fallback: clearing app storage from Android settings, provided `docs/ANDROID.md` explains it.

Do not delete the game's browser identity/reconnect storage when changing servers unless key collisions are proven. If collisions occur, namespace the shell preference separately and document the behavior.

Acceptance criteria:

- Invalid schemes such as `file:`, `javascript:`, and `intent:` are rejected.
- A failed health check never navigates away from the shell.
- A valid server opens inside the app rather than an external browser.
- The last valid server survives an app restart.

## 7. Phase 3 — Android configuration

Update `android/app/src/main/AndroidManifest.xml` and Android resources.

Required:

- `android.permission.INTERNET`.
- `android.permission.ACCESS_NETWORK_STATE` if used by the shell or native connectivity handling.
- App label `Stronghold Protocol`.
- Stable application ID `io.github.r1kk12841.strongholdprotocol`.
- Landscape orientation. Prefer `sensorLandscape` so either landscape direction works.
- Hardware acceleration enabled.
- Backups disabled unless a clear backup policy is added.
- Exported activity declarations compatible with the selected target SDK.

### Cleartext policy

Production servers should use HTTPS/WSS. LAN play currently needs HTTP/WS.

For the MVP:

- allow cleartext traffic only if it is required for LAN testing;
- display the trusted-LAN warning in the server shell;
- document that credentials must never be sent because the game has no account system;
- add a release-hardening task to disable cleartext for a Play build or split LAN and production into Gradle product flavors.

Recommended flavors:

```text
lanDebug     cleartext allowed, debuggable
production   HTTPS only, non-debuggable
```

If flavor work materially delays the MVP, implement cleartext in debug first and track release flavoring as a required pre-publication task.

### App lifecycle

- Keep the WebView alive across ordinary configuration changes.
- Verify that backgrounding and foregrounding do not create a second game session.
- On resume, trigger the same online/focus behavior used by the browser so WebSocket reconnection occurs promptly.
- Do not reload the page automatically on every resume.
- During combat, prevent accidental screen sleep only if a maintained plugin or a very small native implementation can do so without new runtime permissions.

### Back button

Implement deterministic behavior:

1. Close an open game modal/drawer when possible.
2. Otherwise navigate WebView history if safe.
3. Otherwise require a second Back press within two seconds to exit.

Do not let Back accidentally abandon a match.

## 8. Phase 4 — branding and native assets

Create original project branding assets. Do not copy Arknights icons or copyrighted character artwork into the Android launcher icon or splash screen.

Required assets:

- Adaptive launcher icon: foreground and background layers.
- Monochrome icon for supported Android versions.
- Splash screen using the project name and original geometric styling.
- Dark background matching the web UI.

Use the official Capacitor asset-generation workflow supported by the chosen stable version. Document the source SVG/PNG and generation command.

Acceptance criteria:

- No stretched or transparent-edge launcher icon.
- Splash screen works in light and dark system themes.
- No copyrighted game asset is added to Git.

## 9. Phase 5 — compatibility work

Test the existing web client in Android System WebView before changing shared code.

Verify:

- WebGL context creation and fallback renderer.
- PixiJS and Spine loading.
- Three.js lazy loading when optional local board art exists on the server.
- Pointer events, drag deployment, facing wheel, long press, and multi-touch.
- Audio unlock after the first user gesture.
- Fullscreen/safe-area layout with status and navigation bars.
- English/Chinese switch and persistence.
- WebSocket connection, ping, reconnect, background/foreground, and session replacement behavior.
- Invitation URLs containing `?room=KEY`.

Only patch shared web code for reproducible Android WebView defects. Every compatibility patch must also retain normal desktop-browser behavior and include a focused regression test.

Do not add an Android user-agent branch when capability detection can solve the problem.

## 10. Phase 6 — automated tests

Add `test/android-config.test.js`. It should perform read-only/static checks without requiring Android Studio:

- Capacitor dependencies use the same major and exact locked versions.
- `capacitor.config.ts` has the expected app ID, app name, and `webDir`.
- Shell files exist and contain no inline secret.
- URL normalization rejects unsafe schemes and credentials.
- Android manifest contains required permissions and orientation.
- `.gitignore` excludes keystores, `local.properties`, build outputs, and Gradle caches.
- README and `docs/ANDROID.md` contain valid build commands.

Keep current tests passing:

```bash
node --test
```

Add Android build checks:

```bash
npm run android:sync
cd android
./gradlew lintDebug testDebugUnitTest assembleDebug
```

On Windows use `gradlew.bat`.

If a device/emulator is available, add a smoke test with ADB that:

1. installs the debug APK;
2. launches the activity;
3. connects to `http://10.0.2.2:3000`;
4. verifies the title screen appears;
5. changes language to English;
6. backgrounds and resumes the app;
7. confirms the app did not lose its saved server.

Do not make device tests mandatory for contributors without an Android SDK. Keep them behind an environment flag.

## 11. Phase 7 — CI and release build

Create a GitHub Actions workflow for Android that runs on changes to Android, shell, package, or relevant web files.

CI stages:

1. Checkout.
2. Set up the repository's required Node version.
3. `npm ci`.
4. Run focused JavaScript tests.
5. Set up Java/Android SDK versions required by the selected Capacitor release.
6. `npm run android:sync`.
7. Run Gradle lint and unit tests.
8. Build an unsigned debug APK.
9. Upload the debug APK as a workflow artifact.

### Signing

- Never commit `.jks`, `.keystore`, passwords, or `key.properties`.
- Generate the release key outside the repository.
- Store CI signing values only in GitHub Actions secrets.
- Add a checked-in `key.properties.example` containing placeholders only.
- Document local signed AAB generation in `docs/ANDROID.md`.

Expected outputs:

```text
android/app/build/outputs/apk/debug/app-debug.apk
android/app/build/outputs/bundle/release/app-release.aab
```

Before publishing, follow the current official Capacitor/Android deployment guidance rather than copying obsolete target-SDK values:

- <https://capacitorjs.com/docs/android/deploying-to-google-play>
- <https://capacitorjs.com/docs/android/setting-target-sdk>

## 12. Phase 8 — optional Play-ready bundled client

Do this only after the remote-shell MVP is stable and after a design review.

The goal is to bundle the UI/runtime code in the APK while keeping large game assets on a server or asset-delivery system. Required refactor:

1. Add a single runtime configuration module with:
   - `serverOrigin`
   - `wsUrl`
   - `dataBase`
   - `assetBase`
   - `simBase`
2. Replace direct root-relative fetches in `public/js/data.js`, `public/js/assets.js`, `public/js/battle/runner.js`, and related modules with that configuration.
3. Bundle or copy `public/`, `shared/`, and browser-safe `server/sim/` modules into `webDir` while preserving import paths.
4. Add server CORS policy for explicit trusted app origins. Never use unrestricted credentialed CORS.
5. Decide how the 250 MB asset set is delivered:
   - CDN/server streaming with browser cache;
   - an optional downloadable asset pack;
   - Google Play Asset Delivery if publishing through Play.
6. Add a version handshake so a bundled client refuses an incompatible server protocol with a useful error.
7. Add cache invalidation keyed by manifest hash.

Do not package game assets in the APK until licensing, distribution size, update behavior, and rights-holder risk have been reviewed.

## 13. Manual QA matrix

Test at minimum:

| Device/profile | Network | Renderer | Required scenario |
|---|---|---|---|
| Android emulator | `10.0.2.2` HTTP | 2D | Install, connect, solo room, rotate/back/resume |
| Physical mid-range phone | LAN HTTP | WebGL | Full solo round, touch drag, audio, English UI |
| Physical low-memory phone | LAN HTTP | Low/fallback | Repeated prep/combat transitions without crash |
| Physical phone | HTTPS/WSS | WebGL | Co-op join by key, reconnect after backgrounding |
| Tablet | HTTPS/WSS | WebGL | Safe areas, layout, modal sizing, Final Assault |

For each profile verify:

- first launch and saved-server launch;
- Chinese and English;
- room create/join;
- drag, long press, facing selector, shop confirmations;
- audio after first tap;
- five-minute background/resume;
- disconnect/reconnect;
- screen sleep behavior;
- Back button behavior;
- no mixed-content or WebView console errors.

## 14. Definition of done

The MVP is complete only when all are true:

- A fresh clone can produce a debug APK using documented commands.
- The APK installs on a supported emulator and physical Android device.
- The server selector validates, saves, and opens both emulator and LAN server URLs.
- A complete solo game can be played without a desktop-only interaction.
- Two devices can join the same Alliance room and reconnect after backgrounding.
- English and Chinese behave the same as in the browser.
- Existing JavaScript tests pass.
- Gradle lint, Android unit tests, and debug assembly pass.
- No asset bundle, keystore, password, local SDK path, or generated build directory is committed.
- `docs/ANDROID.md` explains prerequisites, build, install, server connection, troubleshooting, signing, and uninstall/reset.
- Credits link to the original [sganggs/Stronghold-Protocol](https://github.com/sganggs/Stronghold-Protocol) repository.

## 15. Instructions for Gemini

Use this section as the execution contract:

1. Implement phases in order. Do not start Phase 8 during the MVP.
2. Inspect existing files and tests before editing. Preserve unrelated changes.
3. Use the latest **stable** compatible Capacitor release and lock exact versions. Do not use `next` documentation or packages in production.
4. Prefer small, testable pure functions for URL validation and platform decisions.
5. Do not rewrite gameplay, networking protocol, simulation, or rendering unless a reproducible Android defect requires it.
6. Do not add game assets, signing credentials, or personal server URLs to Git.
7. After each phase, run the relevant tests and record exact results.
8. When Android SDK/device tooling is unavailable, finish all static work and clearly mark device-dependent verification as pending; do not claim it passed.
9. Keep `README.md`, `README_EN.md`, and `docs/ANDROID.md` synchronized where user-facing commands overlap.
10. End with a report listing changed files, test/build results, APK/AAB paths, known limitations, and the next safe step.
